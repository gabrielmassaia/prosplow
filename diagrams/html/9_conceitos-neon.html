Conceitos — Por que Neon?

Postgres tradicional foi feito para servidores de vida longa. Serverless/edge nasce e morre a cada requisição — Neon resolve esse descompasso.

O problema — serverless + Postgres tradicional

Sem pooling
Requisição 1, 2, 3…N
cada uma sobe uma função efêmera
Cada função abre uma conexão TCP nova
Postgres tem limite fixo (ex: 100)
Pico de tráfego → "too many connections"

A solução — Neon (serverless Postgres + pooling)

Requisições 1, 2, 3…N
funções serverless
Pool singleton — src/infrastructure/db/index.ts
criado uma única vez
Connection pooler do Neon
multiplexa conexões
Neon Postgres — compute serverless
escala para zero quando ocioso

Como ler este diagrama

O pool é criado uma única vez, como singleton — não uma conexão nova por requisição. É esse arquivo que os repositórios recebem por injeção no construtor.
sslmode=require na DATABASE_URL não é opcional — o Neon exige TLS, diferente de um Postgres local em Docker.
"Escala para zero": em dev (ou tráfego baixo à noite), o compute hiberna e você não paga por capacidade ociosa — acorda na próxima query, com pequena latência de cold start.
Branching (não usado ainda no projeto): o Neon permite copiar o banco copy-on-write para testar uma migration arriscada sem tocar em produção.
