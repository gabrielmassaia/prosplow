Conceitos — Por que Next.js?

React puro não decide onde renderizar nem tem roteamento. Next.js resolve os dois: pastas viram rotas, e o servidor renderiza por padrão.

O problema do SPA puro (sem framework)

Navegador
Servidor estático
Bundle JS
GET /prospeccao
HTML quase vazio (&lt;div id=root&gt;)
baixa o bundle inteiro
↻executa React + busca dados (client-side)
Crawlers veem página vazia. Usuário espera o JS baixar + rodar para ver algo.

Ciclo de vida de uma requisição — App Router

GET /prospeccao/campanhas
src/proxy.ts (middleware)
checa cookie / rota pública
app/(protected)/layout.tsx
Server Component
page.tsx — renderiza no servidor
requireUser() + repositório + HTML
HTML + RSC payload enviados
Navegador hidrata só os Client Components
página interativa

Estratégias de renderização

SSR — usado no ProspFlow
Renderiza a cada requisição
dashboard, leads, kanban — dados sempre atuais
SSG — não usado aqui
Renderiza uma vez, no build
ideal para páginas públicas quase estáticas
ISR — não usado aqui
Estático, revalida periodicamente
meio termo entre SSR e SSG

Como ler este diagrama

Next.js resolve dois problemas do React puro: roteamento (pastas em app/ viram rotas) e onde renderizar (servidor por padrão).
src/proxy.ts roda antes de qualquer coisa — primeira parada de toda requisição, antes do React entrar em cena.
Todo Server Component do ProspFlow usa SSR, não SSG — um dashboard de leads muda a cada minuto, não faria sentido gerar uma vez no build.
O RSC payload é a serialização que acompanha o HTML e diz ao navegador quais partes já estão prontas (Server) e quais precisam hidratar (Client).
